## 1. 版本目标

**一句话：把"能跑但数据错乱、体验卡死"的 v1 修成"数据正确、离线可用、隐私可控、可回归测试"的可用版本。**

v2.0 是 **修复 + 补全**，不是换产品：不新增产品品类、不改技术栈、不改桌面形态、不改入口命令、不改"昵称即登录"的身份模型。所有需求的来源都是审计报告给出的缺陷编号，禁止在此之外自行扩展功能。

三个正交目标：

1. **数据正确**：泡泡墙/详情/对话显示的信息与数据库真实内容 100% 一致，旧库 6 条记录不丢、不错位。
2. **体验不卡**：网络故障不影响界面响应，断网也能浏览与创作，恢复后自动补齐。
3. **边界可信**：单次回复、私聊隐私、作者权限这三条规则由服务端强制执行，不依赖客户端自觉。

## 2. 产品定义

### 2.1 用户故事

| # | 角色 | 故事 |
|---|------|------|
| U-1 | 普通浏览者 | 作为普通浏览者，我希望泡泡墙上的每张卡片都能看到内容、情感颜色、发布时间和回复模式，以便我一眼判断哪个泡泡值得点开。 |
| U-2 | 普通浏览者 | 作为普通浏览者，我希望按情感分类筛选、按关键字搜索，以便快速找到与我当下心情相关的内容。 |
| U-3 | 普通浏览者 | 作为普通浏览者，我希望新泡泡不要打断我正在看的内容，只在底部提示"有 N 个新泡泡"，以便我自己决定何时刷新。 |
| U-4 | 泡泡发布者 | 作为发布者，我希望在"我的"里找到我发布的、公开保留的、私密保存的全部泡泡，以便我不会再丢失自己写下的东西。 |
| U-5 | 泡泡发布者 | 作为发布者，我希望只有我能看到"已解决""申请保留"按钮，以便别人不能替我结束或处置我的泡泡。 |
| U-6 | 泡泡发布者 | 作为发布者，我希望点"已解决"后泡泡有一个爆破动画再消失，以便这个结束动作有情绪上的收束感。 |
| U-7 | 泡泡发布者 | 作为发布者，我希望打开对话窗口时对方是真正的对话方而不是我自己，以便我能正常回复关心我的人。 |
| U-8 | 回复者 | 作为回复者，我希望在单次回复的泡泡上回复一次后，界面明确告诉我"已回复过"，以便我不用反复尝试。 |
| U-9 | 回复者 | 作为回复者，我希望我对"短时对话框"泡泡发的消息只有我和作者能看见，以便我敢说真话。 |
| U-10 | 回复者 | 作为回复者，我希望对话里我能分清哪句是我说的、哪句是对方说的，并且知道对方还没回，以便我不必猜。 |
| U-11 | 离线用户 | 作为离线用户，我希望服务器挂了或断网时软件不卡、不闪退，并能看到本地缓存，以便网络不好时也能用。 |
| U-12 | 离线用户 | 作为离线用户，我希望断网时发的泡泡和回复先存本地、联网后自动发出去，以便我不用记得手动重发。 |

### 2.2 硬性约束（不可协商，直接进入架构与验收）

| 编号 | 约束 |
|------|------|
| C-1 | 技术栈保持 PyQt5 + Flask + SQLite；不引入前端框架；保持"双击即用"的 Windows 桌面形态。 |
| C-2 | 入口命令不变：`python server.py` 启动服务器，`python src/main.py` 启动客户端。 |
| C-3 | **必须兼容本机已有数据库**：客户端 `~/.Qingyuan/qingyuan.db` 现有 **6 条泡泡记录**（Tester×3、A×2，另 1 条 test-pub-003），升级后 6 条全部可见、字段不错位、id 不变；服务端 `server_data/qingyuan_server.db` 现有 5 条泡泡 / 1 条回复 / 2 条对话同样不得丢失。 |
| C-4 | 全部 UI 文案中文；不得出现 `??`、`??????` 之类乱码。 |
| C-5 | 用户身份仍是"昵称即登录"，**不引入密码、不做注册流程**。 |

### 2.3 身份与作者归属（P0 前置产品决策）

C-5 保持"昵称即登录"，但 v1 因此无法回答"这条泡泡是不是我发的"，这是审计报告 P0-5/P0-6 无法修复的根因。v2.0 的产品决策：

- **决策 1**：客户端每次启动生成/复用一个**设备级身份标识**，与昵称一同随请求提交；服务端以此判定"请求方是谁"。
- **决策 2**：**昵称仍是用户可见的唯一身份**，界面上不出现 ID、不要求用户输入任何额外信息。
- **决策 3**：服务端必须能判定以下三件事，否则 R-02 / R-05 / R-06 / R-07 无法验收：
  1. 这条泡泡的作者是不是请求方（决定管理按钮可见性、决定谁可执行解决/保留）；
  2. 单次回复是否已被"同一个请求方"用过；
  3. 请求方是否是某个对话的参与者。
- **决策 4**：昵称重名视为同一用户（这是"昵称即登录"的已知代价，v2.0 接受，不做唯一性校验）。
- 具体用 token / node_id / 请求头怎么实现，由架构师决定，PRD 不作规定。

### 3.1 P0（10 条，逐条对应审计报告第四节验收基线，无遗漏、无降级）

| 编号 | 需求描述 | 验收标准（可测试） | 缺陷编号 |
|------|----------|--------------------|----------|
| R-01 | 泡泡墙任意卡片必须正确显示四项信息：正文、情感专属配色与图标、发布时间（`YYYY-MM-DD HH:MM`）、回复模式徽标 | 用本机现有 6 条记录打开泡泡墙：6 张卡片的四项信息全部非空；情感配色等于该情感定义的色值（出现灰色 fallback 的次数 = 0）；时间字符串非空且可被 `datetime` 解析 | P0-1 |
| R-02 | 新增"我的"页面，含三个分组：我发布的 / 公开保留 / 私密保存；私密内容仅本人可见 | ① 本机库中 author=Tester 的记录全部出现在"我发布的"；② 对任一泡泡执行"私密保存"后，它从公开泡泡墙消失，并出现在"私密保存"组，可点开看到原文 + 全部回复 + 全部对话；③ 切换为其他昵称后，该泡泡不出现在任何列表，也无法通过详情页打开 | P1-1 / P0-2 |
| R-03 | 所有网络请求移出 UI 线程；服务器不可达时界面保持响应并显示明确离线提示 | ① 关闭服务器进程后，点击任意卡片进入详情耗时 < 300ms，切换情感筛选 < 200ms；② 窗口拖动、滚动无冻结；③ 3 秒内顶栏出现"⚠️ 离线"标记；④ 连续运行 60 秒，主线程单次阻塞 > 500ms 的次数 = 0 | P0-3 |
| R-04 | 断网期间的发布与回复进入本地待同步队列，网络恢复后自动补同步 | ① 断网时发布 1 条泡泡 + 回复 1 条，界面上有"待同步"标记；② 恢复服务器后 30 秒内自动同步，服务端库出现该泡泡与该回复，"待同步"标记消失；③ 反复触发不产生重复记录（按 id 幂等） | P1-4 |
| R-05 | 单次回复规则由服务端强制：同一身份对同一 `single` 泡泡第二次回复被拒绝（HTTP 409），客户端给出友好提示 | ① 同一身份第二次 `POST /api/bubbles/<id>/reply` 返回 **409**；② 客户端弹中文提示"这个泡泡只能回复一次哦～"，输入框内容不清空、不新增记录；③ 服务端该泡泡的回复记录数 = 1；④ 不同身份仍可各自回复一次 | P0-6 |

| R-07 | 对话窗口的收件人必须是真正的对话对方 | ① 作者打开"我发布的"泡泡的对话窗口，标题显示对方昵称（≠ 作者本人），发出的消息 `receiver` = 对方昵称；② 回复者打开时 `receiver` = 作者；③ 双方各发 2 条后，双方都看到 4 条消息，且"我方消息在右、对方消息在左"的归属 100% 正确 | P0-4 |

| R-09 | 建立 `pytest` 测试套件，全绿 | `pytest` 退出码 = 0，且至少覆盖 4 个模块：数据库读写与迁移（旧库升级后 6 条记录不丢、字段不错位）、单次回复规则（409）、私聊隔离（403）、离线队列补同步；可生成覆盖率报告 | P2-1 |
| R-10 | 一键启动脚本可用，不依赖硬编码绝对路径 | ① 双击 `启动软件.bat` 无 `??????` 乱码；② 脚本内不出现写死的 Python 安装路径（改用 `py`/`python` 查找或 `where python`）；③ 项目整体复制到另一路径（如 `D:\test\情缘项目`）后同样能一键启动 | P2-4 |

## 4. 交互规格

统一约定：所有流程均为窗口内页面切换（不弹新窗口，对话窗口除外）；任何网络动作都不阻塞界面；所有提示文案为中文。

### 4.1 泡泡墙

| 状态 | 界面表现 | 用户可做的操作 |
|------|----------|----------------|
| 首次加载中 | 顶栏正常显示，内容区显示"正在寻找泡泡…"，窗口可拖动 | 拖动窗口、切换用户、切到"我的" |
| 在线 · 有数据 | 自适应网格；每卡片 = 情感图标 + 正文前 80 字 + 情感色底 + 发布时间 + 模式徽标 + 回复数；顶栏"🟢 在线" | 点卡片进详情、切筛选、搜索、发布、切"我的" |

| 访客 · 对话模式 | 显示"💬 发起对话"按钮 + 首条消息输入框 | 发首条消息 → 进入对话窗、返回 |
| 访客 · 作者是自己之外 | 不出现任何管理按钮（已解决/保留） | 回复或返回 |
| 申请保留弹窗 | 两个互斥选项："🔓 公开保留（其他人也能看到）""🔒 私密保存（仅自己可见）"，未选则确定按钮禁用 | 选择 → 确定 / 取消 |
| 私密保存完成后 | 泡泡从公开墙消失；"我的 → 🔒 私密保存"可打开；详情页顶部显示"🔒 私密保存 · 仅自己可见" | 查看 / 返回 |
| 公开保留完成后 | 泡泡仍在墙上，卡片带"📦 已保留"标记 | 查看 / 返回 |
| 已解决 | 播放 ≥600ms 爆破动画 → 返回泡泡墙并提示"泡泡已炸掉 💥" | 返回 |
| 离线打开 | 立即渲染本地缓存（< 300ms），顶部黄条"离线：内容可能不是最新" | 回复（入队待同步）、返回 |
| 泡泡已不存在 | 显示"这个泡泡已经不在了 🌫️" + 返回按钮 | 返回 |

## 5. 明确不做的事（Out of Scope）

| 不做的事 | 理由 |
|---|---|
| 账号 / 密码 / 手机号注册登录 | 违反 C-5；v1 的产品假设是"输入昵称即进入"，加账号体系会推翻整个身份模型与首屏流程。身份问题用 2.3 的决策解决，不加登录墙。 |
| 图片 / 语音 / 视频 / 文件消息 | 需要对象存储、上传进度、内容审核，与"最小代价优先"冲突；纯文字已能满足情感表达。 |
| 群聊 / 多人对话 | 现有数据模型是"泡泡 ↔ 一对一对话"，改成多人要重做表结构与权限，风险远大于收益。 |
| P2P 直连（v1 文档 3.2 节提到的"无需中央服务器"） | 实际实现已是 Flask 中央服务器 + 本地缓存，v2 明确以中央服务器为准；改 P2P 需 NAT 穿透、发现机制，属于换架构，不在本次范围。PRD 以此节为准，v1 文档 3.2 节作废。 |
| 移动端 / Web 端 | 交付形态是 Windows 桌面（PyQt5），跨端等于重写。 |
| 深色模式 / 主题换肤 | 纯视觉增量，不解决任何审计缺陷；当前梦幻浅色主题已满足 v1 3.3 节要求。 |
| 好友、关注、用户主页、主动找人 | 违反 v1 2.7 节"不主动搜索其他用户，所有互动通过泡泡进行"的产品设定。 |
| 推送通知（系统托盘/邮件） | 需要额外系统集成，v2 用轮询 + 未读标记已能覆盖"有新泡泡"的感知需求。 |
| 消息撤回 / 编辑 / 删除单条消息 | 情感场景下撤回忆会破坏对话完整性，且增加同步冲突处理复杂度。 |
| 数据导出 / 云备份 / 换机迁移 | 私密泡泡的"仅自己可见"目前靠本地库实现，云备份会立刻引出加密与合规问题，需单独立项。 |
| 内容审核 / 举报 / 屏蔽 | 需要运营后台与策略，超出本次"修复 + 补全"范围。 |
| 多语言（i18n） | C-4 明确全中文。 |
| 情感标签自定义扩展 | v1 提过"分类可扩展"，但扩展要动配色、图标、筛选、DB 约束四处，本版固定 6 类。 |

## 7. 给架构师的三个提醒

1. **先定数据契约再改代码**：客户端库列序（`id, author_nickname, content, emotion_tag, reply_mode, status, created_at, resolved_at, author_node_id`）与服务端库列序不一致，是 P0-1 的根因；迁移必须"建新表 → 按列名拷贝 → 换表"，且迁移前先备份 6 条记录。
2. **权限规则只在服务端算一次**：R-02/R-05/R-06/R-07 四条必须共用同一套"请求方身份 + 参与者判定"，客户端只做展示，不做判定。
3. **离线能力是横切关注点**：R-03 与 R-04 会改到网络层、UI 刷新、数据库三处，建议先落地"请求统一出口 + 待同步队列"再改页面，否则后面每个页面都要返工。
